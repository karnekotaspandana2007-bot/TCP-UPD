🔵 TCP (Transmission Control Protocol) Overview

TCP is a connection-oriented, reliable byte-stream protocol. It establishes a three-way handshake (SYN, SYN-ACK, ACK), guarantees in-order delivery, uses acknowledgements and sequence numbers, and implements flow control and congestion avoidance. Our client communicates with the server using length-prefixed framing to guarantee clean message boundaries over raw byte streams.

🟠 UDP (User Datagram Protocol) Overview

UDP is a connectionless, lightweight datagram protocol. There is no three-way handshake, no acknowledgements built into the transport layer, and no automatic retransmissions. Datagrams are transmitted independently with minimal header overhead (8 bytes vs 20+ bytes in TCP). For measurement, our application layer tracks sequence numbers and simulates lost packets via timeouts.

🪣 Leaky Bucket Algorithm

The Leaky Bucket algorithm shapes bursty network traffic into a constant, uniform output flow. It models a bucket with a small hole in the bottom. Incoming packets enter a finite buffer (the bucket). Regardless of how fast or irregularly packets arrive, they leak out at a fixed rate. If incoming bursts exceed the bucket capacity, excess packets overflow and are dropped.

🎟️ Token Bucket Algorithm

The Token Bucket algorithm allows controlled bursts of traffic while enforcing an average rate limit. Tokens accumulate in a bucket of fixed capacity at a steady rate. A packet can transmit only if sufficient tokens are present in the bucket. Unlike Leaky Bucket (which forces a strictly uniform rate), Token Bucket allows instantaneous bursts if tokens have accumulated during idle periods.

📈 Educational TCP Congestion Control Simulator

Note: This is a visual simulation of the TCP Reno/Tahoe congestion control model, demonstrating how the sender dynamically estimates network capacity via cwnd (Congestion Window) and ssthresh (Slow-Start Threshold) without probing the OS kernel directly.
  • Slow Start: Exponential growth (doubles each RTT) until cwnd == ssthresh.
  • Congestion Avoidance: Additive Increase (linear growth, +1 MSS per RTT) to gently probe link bandwidth.
  • Timeout Event: Severe loss! ssthresh is halved, and cwnd collapses back to 1 MSS.
  • Fast Retransmit & Recovery (3 Dup ACKs): Moderate loss! cwnd is halved without dropping to 1, continuing directly into Congestion Avoidance.

1. Project Objectives

This system provides an end-to-end framework for analyzing Transport Layer protocols and Network Layer traffic-shaping algorithms. It pairs real operating system Python socket communication (over TCP and UDP) with mathematical performance calculations, traffic policing simulations (Leaky Bucket, Token Bucket), and visual congestion control modeling.

2. Performance Metrics & Mathematical Formulas

Throughput (Mbps) = (Successfully Received Payload Bytes × 8) / Elapsed Seconds / 1,000,000

Note: Calculates strictly application-layer useful payload data throughput (goodput), excluding framing overhead.

Packet Loss (%) = ((Sent Packets − Received Unique Packets) / Sent Packets) × 100
Delivery Ratio (%) = (Received Unique Packets / Sent Packets) × 100
Average RTT = Σ (Valid Round-Trip Times) / Number of Valid Measurements

3. Frequently Asked Examiner Viva Questions

Q1: Why does TCP require message framing while UDP does not?

Answer: TCP is a stream-oriented protocol with no concept of message boundaries; data sent in multiple send() calls may arrive combined in a single recv() call (or fragmented). Therefore, an application-layer framing mechanism (such as our 4-byte length prefix) is required. Conversely, UDP is datagram-oriented where each sendto() maps to an intact datagram up to MTU/buffer size.

Q2: What is the fundamental difference between Leaky Bucket and Token Bucket?

Answer: Leaky Bucket enforces a strictly constant, uniform output rate regardless of burstiness, which can increase latency for bursty traffic. Token Bucket allows instantaneous bursts up to bucket capacity if tokens have accumulated during previous idle periods, while still bounding the long-term average rate to the token generation rate.

Q3: Why does TCP Congestion Window grow exponentially during Slow Start?

Answer: In Slow Start, for every acknowledged packet, the sender increases cwnd by 1 MSS. Since an entire window of packets is acknowledged per RTT, the window doubles every RTT ($2^n$ growth), rapidly ramping up to utilize available network capacity until hitting ssthresh.

Q4: Why does Fast Recovery cut cwnd in half instead of dropping to 1 MSS?

Answer: Receiving 3 duplicate ACKs proves that packets are still reaching the receiver (the "ACK clock" is still ticking), indicating mild packet loss rather than total network collapse. Resetting to 1 MSS would needlessly cripple throughput, so Reno halves cwnd and resumes linear Congestion Avoidance.
